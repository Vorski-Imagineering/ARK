## Executive synthesis

The field has moved quite sharply in early 2026. The most important shift is structural, not cosmetic: serious agent systems are separating the **harness/control plane** from the **execution plane** and from the **memory plane**. entity["company","OpenAI","ai company"] now frames sandbox agents explicitly around a harness-versus-compute split; entity["company","Anthropic","ai company"] has made the same move with Managed Agents and its recent harness-design writing; and entity["company","Microsoft","software company"] has folded multi-agent execution, checkpoints, and human gates into a graph-based workflow framework rather than leaving them as prompt tricks. For your use case, that matters because “institutional memory through agent conversation” is not primarily a tool-calling problem. It is a **memory compilation** problem. Conversation transcripts are high-volume, low-signal, temporally evolving raw material. The winning architecture is therefore not just a better agent loop; it is a loop that writes into a **temporal memory graph** and then compiles that graph into higher-order artefacts: summaries, claims, contradictions, unresolved questions, people-topic affinities, and matching recommendations. That is exactly the direction implied by entity["people","Andrej Karpathy","ai researcher"]’s LLM wiki pattern, OpenClaw’s memory-wiki layer, Zep/Graphiti’s temporal context graphs, Neo4j’s three-layer agent memory, and SurrealDB’s Spectron thesis. citeturn21view0turn7view0turn8search0turn35view0turn35view1turn33view0turn34search20turn22search3

It already assumes GitHub as the editable layer, SurrealDB as the queryable brain, an MCP sidecar, webhook-driven incremental ingestion, and a graph schema for documents, chunks, concepts, communities, and relations. ## OpenClaw

OpenClaw is the most directly relevant starting point because it already thinks in the right primitives for conversation-native agents: sessions, channels, isolated workspaces, multi-agent routing, and organisational delegates. Its runtime serialises one full agentic loop per session, persisting intake, context assembly, inference, tool execution, streaming, and final state. Multi-agent mode isolates workspace, state directory, auth profiles, and session store per agent, which is exactly the sort of boundary you want when modelling different institutional roles or conversation domains. Its delegate architecture then takes that personal-assistant core and extends it into explicit organisational delegation tiers: read-only draft, send-on-behalf, and proactive action, all under separate identities rather than agent impersonation. citeturn7view4turn7view1turn7view2

The memory design is unusually important. OpenClaw stores durable memory in plain files, but it does not stop there. It supports hybrid semantic-plus-keyword memory search, automatic memory flush before compaction, optional “dreaming” to consolidate short-term into long-term memory, and—most importantly for your use case—the `memory-wiki` companion layer. That wiki layer compiles memory into deterministic pages with structured claims, evidence, contradiction tracking, freshness tracking, dashboards, and machine-readable digests. In other words, OpenClaw already contains a native precursor to the compiled-memory architecture you want. citeturn7view0turn8search0turn8search2

Its evolution in 2026 is also revealing. The January launch post frames the product lineage from Clawd to Moltbot to OpenClaw. Since then, the public signals have concentrated on organisation-scale operation and hardening rather than on cute demos: a formal MITRE ATLAS threat model in February, a VirusTotal-backed skill scanning pipeline in February, and docs that lean heavily into delegate identity, bound channels, skill isolation, and marketplace safety. That is not where a toy project goes. That is where a system goes when it is trying to become a serious agent operating environment. citeturn10search2turn10search1turn10search0

My read on its projected trajectory is therefore an inference, but a fairly grounded one. OpenClaw looks likely to evolve toward a **secure, message-native delegate platform** for individuals and small organisations, with a stronger plugin supply chain, more formal policy around skills and channel actions, and a richer compiled knowledge layer attached to its session memory. For a transcript-first institutional memory system, that makes OpenClaw a strong **edge runtime** and a decent experimental **knowledge compiler**, but not yet the cleanest core analytics plane by itself. The place where it shines is at the boundary between humans and conversations; the place where you will still need more structure is cross-conversation synthesis at community scale. citeturn7view2turn7view1turn7view0turn10search0turn10search1

## Hermes

Hermes, built by entity["company","Nous Research","ai research company"], is the most ambitious “agent that improves itself over time” system in this set. Its official positioning is explicit: a built-in learning loop, persistent memory across sessions, skill creation from experience, and deepening user models. Architecturally, Hermes consolidates CLI, gateway, ACP/editor integration, batch mode, and API server around one `AIAgent` core. It also exposes a very broad tool registry—web, browser, terminal, delegation, memory, cron, RL environments—and treats profile isolation as a first-class boundary. citeturn11search0turn11search2turn12view1turn12view2

The reason Hermes matters for your project is not just that it can remember. It is that it is designed to **accumulate procedural competence** as well as factual memory. Delegation is explicit and parallelisable; persistent memory is native; session search is built in; and the memory provider interface is extensible, with official support for multiple backends including Honcho, Mem0, Hindsight, and others. This makes Hermes unusually strong if you want agents that do reflective work over transcripts, build reusable “sense-making skills”, and then apply those skills in later runs. citeturn13search0turn13search2turn13search14turn12view4

There are two caveats. The first is governance. A self-improving agent is not just a memory system; it is a moving target. The official repository already contains active discussion about “receipts” for self-improving agents—essentially, how to prove which skill version produced which behaviour. That is not a minor issue. For institutional memory, provenance is oxygen. If you cannot show which extractor, summariser, or matching policy created a belief, you will eventually build a very elegant hallucination engine. citeturn11search5

The second caveat is architectural fit. Hermes is exceptionally strong as a **personal or team-side autonomous runtime**. It is weaker as a clean, centrally governed institutional memory substrate unless you impose more structure on top of it. Its recent v0.10 release added a Tool Gateway and continued consolidating the runtime, which suggests a trajectory toward a provider-agnostic, always-on agent operating system rather than a narrowly defined enterprise workflow engine. That is exciting. It is also exactly why I would use Hermes as a **learning-capable front end or specialist summarisation worker**, not as the sole source of institutional truth. citeturn12view0turn12view1turn12view2

## LangGraph, OpenAI Agents SDK, and Microsoft Agent Framework

### LangGraph

LangGraph, from entity["company","LangChain","ai software company"], is the best open-source answer if your real problem is “how do I turn agent behaviour into a durable system?” rather than “how do I make an agent feel alive?”. Its primitives are exactly the boring things that become precious in production: threads, checkpoints, interrupts, subgraphs, replay, state history, and fault tolerance. It persists graph state at every step, supports human-in-the-loop review through interrupts, and treats subgraphs as reusable building blocks for multi-agent systems. citeturn15view0turn15view1turn15view2turn15view3

For the Coherence-style conversation use case, LangGraph’s real advantage is that it gives you a **workflow brain** rather than a character. That means you can model transcript ingestion, entity extraction, contradiction review, weekly synthesis, matchmaking candidate generation, and human approval as separate nodes or subgraphs, each with their own checkpointed state. If something fails at the ninth step, you do not start again from zero like a caffeinated goldfish. You resume. That is a massive practical advantage for institutional memory pipelines. citeturn15view0turn15view1

The trade-off is that LangGraph is not opinionated about the memory substrate. That is both its magic and its tax. You still need to choose the actual memory plane—SurrealDB, Neo4j, Zep, or something else—and build the domain schema yourself. If you want a tidy, turnkey “assistant in Telegram” experience, OpenClaw or Hermes will feel more complete. If you want the most defensible orchestration core for long-horizon transcript processing, LangGraph is the strongest of the open systems here. citeturn15view3turn14search0

### OpenAI Agents SDK

The OpenAI Agents SDK has sharpened quickly in 2026. Its core abstractions—agents, tools, handoffs, guardrails, sessions, and tracing—are deliberately lean, but the April sandbox-agent release changed its strategic role. The SDK now makes the harness-versus-sandbox boundary explicit: the outer runtime owns turns, approvals, tracing, handoffs, and recovery, while the sandbox owns files, commands, ports, and resumable workspace state. Built-in tracing records generations, tool calls, guardrails, and handoffs by default, and handoffs themselves are encoded as tools exposed to the model. citeturn17view0turn17view1turn17view2turn17view3turn17view4

Why this matters for you: if you want to keep the orchestration layer small and legible while attaching a serious external memory system, this SDK is an excellent **control-plane shell**. It is particularly attractive if you want clean observability, resumable workspaces, and a service architecture where transcript analysis jobs run against mounted corpora or generated artefacts. The March API changelog also points in the same direction with tool search and native compaction for longer-running workflows. citeturn16search6turn17view3

Its weakness is obvious. It does not solve institutional memory for you. Sessions preserve conversational state; sandbox memory preserves lessons from prior workspace runs; but you still have to design the graph, the summarisation layer, and the retrieval policy you care about. In effect, the OpenAI SDK is a very good steering wheel. You still need to build the car. Zen humour aside, steering wheels matter. citeturn17view0turn17view3

## Memory, compiled knowledge, and graph systems

Karpathy’s LLM wiki idea is the cleanest conceptual frame for your memory layer. The key move is not “retrieve better chunks”. It is “compile raw sources into a persistent, interlinked wiki that compounds over time”. His raw/wiki/schema split is particularly apt for your case: **transcripts as raw episodes**, **compiled pages as durable memory**, and **schema instructions as the discipline that keeps the compiler honest**. For your use case, I would treat this idea as a **synthesis layer above** graph and vector memory, not as a replacement for them. If you stop at the wiki, you lose graph-native analytics. If you stop at the graph, you lose human-legible cumulative sense-making. You need both. citeturn21view0

The best current memory systems for transcript-first institutional intelligence are therefore the ones that combine four properties: temporal facts, provenance, hybrid retrieval, and some path toward compiled synthesis. ## Recommended architecture for Genesis Brain

Your current design already contains the right bones: GitHub as editable layer, webhook-driven incremental reindexing, Kreuzberg text extraction, embeddings, LLM concept-and-relation extraction, SurrealDB upserts, MCP/REST access, and the existing OpenClaw gateway on the VPS. The file also argues, sensibly, that SurrealDB is still the right database at your current scale and that the real question is whether to deepen rather than switch. I agree with that assessment. fileciteturn1file1 fileciteturn1file9 fileciteturn1file2 fileciteturn1file6

The biggest improvement is conceptual: **make transcripts the primary source object**, not just another document. That means adding an immutable episode layer with `conversation`, `turn`, `speaker`, `channel`, `reply_to`, `timestamp`, `attachments`, and `conversation_id`, and then deriving higher-order objects from that stream. The current schema of `document`, `chunk`, `concept`, `community`, and edges is a good foundation, but it needs to expand into institutional primitives: `claim`, `evidence`, `decision`, `commitment`, `question`, `interest`, `person_topic_affinity`, `person_project_affinity`, `summary`, `match_candidate`, `contradiction`, and `trend_shift`. This is the difference between a knowledge graph and an organisational mind. fileciteturn1file9 citeturn35view1turn33view0turn34search20

I would implement the improved version as four tightly coupled layers.

The first layer is the **episodic ledger**. Every transcript turn is stored append-only with provenance, confidence, thread identity, and access controls. No memory compiler should be allowed to overwrite the raw episodes. Karpathy’s “raw sources are immutable” rule is exactly right here. citeturn21view0

The second layer is the **temporal graph memory**. Extraction jobs convert episodes into entities, claims, relations, interests, projects, asks, offers, and decisions, all with valid-from/valid-to semantics and evidence links back to transcript turns. This is where systems like Graphiti, Neo4j Agent Memory, and Spectron point the way. It is also where your current SurrealDB-based design can be upgraded without replacing the database. citeturn35view0turn35view1turn33view0turn34search20

The third layer is the **compiled wiki and summary plane**. Here I would be very explicit: daily room summaries, weekly thematic summaries, entity pages, project pages, people pages, unresolved-question pages, contradiction dashboards, and “what changed this week?” pages. OpenClaw’s memory-wiki and Karpathy’s LLM wiki both support this pattern directly. Summaries produced during Q&A should themselves become candidate artefacts in this layer rather than evaporating into chat history. citeturn8search0turn21view0

The fourth layer is the **sense-making plane**. This is where you compute outliers and matchmaking. Outliers can be scored using rarity, contradiction, sudden change in topic affinity, unusual cross-community edges, or unsupported claims that appear in one conversation but not the wider graph. Matchmaking can be scored with time-decayed person-topic edges, shared questions, complementary offers and needs, and bridge centrality between weakly connected clusters. This is an inference from the graph architectures above, but it is the exact kind of inference those architectures are meant to enable. citeturn33view0turn35view0turn34search20

On harness choice, my recommendation is equally concrete. **Keep OpenClaw as the live conversation edge in the near term**, because you already have `openclaw-gateway` in the plan and OpenClaw’s session, routing, and delegate model are naturally aligned with messaging channels. Add a **LangGraph service behind it** to own the institutional workflows: transcript compilation, contradiction review, nightly and weekly synthesis, and human-approved publication into the compiled wiki. Keep **SurrealDB as the canonical memory store** for now. Only add Neo4j later if graph analytics, provider ecosystem, or BI integration become more important than one-engine simplicity. fileciteturn1file1 fileciteturn1file8 citeturn7view2turn15view0turn15view1turn34search18

If you prefer the Hermes route, I would use it differently: Hermes becomes a **specialist reflective worker** that reads transcript batches, proposes new skills for sense-making, and writes back structured artefacts into the canonical memory plane. That is a good experimental path. It is not the one I would let govern the whole institution until provenance controls are stronger. citeturn11search0turn11search5turn12view4

So the recommended stack, stated plainly, is this:

**Best overall fit now:** OpenClaw at the edge, LangGraph in the middle, SurrealDB plus compiled wiki as memory. citeturn7view1turn15view0turn34search20turn21view0

## Open questions and limitations

A few things remain genuinely unresolved.

There is still no strong independent benchmark that directly compares SurrealDB Spectron, Zep/Graphiti, Neo4j Agent Memory, Letta, and Mem0 on **institutional transcript tasks** like cross-conversation contradiction discovery, social matchmaking usefulness, or outlier precision. Most hard numbers in this space are vendor-produced and concentrated on memory benchmarks such as LoCoMo, DMR, and LongMemEval. Useful, yes. Final truth, no. citeturn23search0turn25view0turn25view2

OpenClaw’s public materials are rich on architecture and security but thinner on a formal forward roadmap beyond implication. So the trajectory I gave is reasoned inference, not a published roadmap item. Hermes has the opposite personality: lots of velocity and visible surface area, but some of its most important governance questions are still being worked through in public issues rather than settled product guarantees. citeturn10search2turn10search1turn11search5turn12view0

The most important unanswered question for you is therefore not vendor choice. It is evaluation design. Before locking anything in, you should define a benchmark over your own transcript corpus that measures: cross-thread recall, fidelity of weekly synthesis, contradiction detection, precision of “who should talk to whom?”, and usefulness of surfaced outliers. Without that, the stack choice will feel like philosophy. With it, it becomes engineering. citeturn19search20turn15view0turn33view0
